Why this is calmer, and why it scales

The current builder is one long column: details, settings, generator, sections, questions, preview. Every feature is added to the same scroll, so adding a feature makes the page heavier. This mockup keeps the same data and the same actions but divides them across a fixed shell, then hides depth behind four predictable levels of disclosure. The two edge states — an empty first-run test and a read-only shared test — are drawn with the same shell and real German/French copy, so the layout is proven against longest-case translations rather than English strings.

Zone 1

Outline rail

  • Whole test at a glance
  • Parts & questions nest; drag to reorder
  • Jump-to search, status dots
  • Add / insert-from-bank actions
Zone 2

Focus pane

  • Exactly one thing open: overview, part, or question
  • Overview = name + 4 setting tiles + structure
  • Question = prompt + one answer module + folded extras
  • Readiness gets its own screen
Zone 3

Preview

  • Student view or A4 paper
  • Zoom, answer key, points, print
  • Becomes the per-type guide on a question
  • Collapses behind one topbar button
1 · Visible The five things a teacher needs every time: name, mode, time, scoring, structure.
2 · Chip row “More options” answered per question: media, hint, tagging, scoring, language.
3 · Accordion Within a part: passage, audio, playback options, routing.
4 · Drawer / dialog Test-wide settings in five tabs; question types in the picker.

Rules that keep it scalable

RULE 01

A new capability never adds a top-level block

It lands in one of five places: a settings tab, a More-options chip, a part accordion, the preview, or Checks. The overview keeps its three cards.

RULE 02

One answer module at a time

Nineteen question types × all their fields, with only one mounted. A twentieth type costs one module component and one picker tile.

RULE 03

Mode changes content, never layout

Placement reveals routing and generator; practice reveals category and retakes. The shell, rail and preview stay identical, so teachers learn one screen.

RULE 04

Depth is earned, not stacked

Visible → chip → accordion → drawer → dialog. New optional settings start folded; nothing optional sits open by default.

RULE 05

The rail is the table of contents

Nesting plus search plus status dots keeps a 60-question test navigable, and gives drag & drop a home that does not compete with the editor.

RULE 06

Problems have one address

Readiness is a screen with links, not a growing stack of banners. The topbar pill is the only persistent reminder.

Open decisions

  • Save behaviour. The mockup keeps today’s explicit Save plus the unsaved-changes guard. Should the focused editor autosave a draft per item instead?
  • One-level nesting. Parts contain questions, as now. Deeper nesting (sections in sections) would need a tree policy and routing semantics first.
  • Rail versus inline editing. The mockup treats the rail as navigation and the centre as editing. If inline editing is preferred, the rail search and drag handles still hold.
  • Large tests. The rail should virtualise beyond roughly 150 rows; the mockup assumes it.
  • Copy and i18n. New strings (zone headings, “More options”, “Checks”, tile labels) need keys in all five locales, and the docs page plus README need the matching feature line — same as the #1210 checklist.
  • Tour targets. The four existing tour steps need new anchors; the picker and answer modules carry their #1210 test ids unchanged.

Mockup only. No components, types, storage, locale files or tests were touched; this file exists to agree the layout before implementation. Palette, fonts, radii and control styling are copied from src/index.css so the mockup and the app cannot drift visually.
